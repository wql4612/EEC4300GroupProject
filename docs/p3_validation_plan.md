## 3. 实验矩阵与 Seed 映射

**5 组 × 4 查询 × 3 rollout seeds × 3 Prompt = 180 个计划槽位。** 每个 Prompt 60 槽、每个组–种子配对块 12 槽。基础模型沿用 D2 的 `qwen2.5:3b` Q4_K_M，完整 digest 为 `357c53fb659c5076de1d65ccb0b397446227b71a42be9d1603d46168015c9e4b`。温度为 **0.6**，`num_predict=128`，`num_ctx=4096`，`stream=false`，沿用 D2 的模型默认采样配置和模板。D2 的模型模板 SHA-256 为 `eb4402837c7829a690fa845de4d7f3fd842c2adee476d5341da8a46ea9255175`。审批后须重新核对实际运行时的模型、模板和参数，出现差异时暂停启动并提交审核。

运行顺序为种子 `42 → 271828 → 314159`，每个种子内按 `H1 → H2 → H3 → H4 → H5`。设 `s` 为 0 基种子序号，`g` 为 0 基组序号，`q` 为 1 基查询槽。每槽的模型 seed 是 `rollout_seed + 4*g + (q-1)`，三版共享此值。按照 `(s+g) mod 3` 左旋 `[P1,P2,P3]`，在块内每槽依次请求三个条件，再推进下一槽。三个条件各在每个执行位置出现 5 个配对块。每条轨迹用 `(Prompt, Group ID, rollout_seed, block_attempt)` 隔离历史，首槽为空，仅纳入自身先前完整模型响应中由官方 Parser 提取的候选。提取成功的越界候选仍可留在自身历史，沿用 D2。

**基础设施故障沿用 D2。** 每个块的每个尝试中，每槽最多发一次请求，关闭隐式重试与重定向。首轮 12 槽中若有至少 2 次传输错误、HTTP 失败、无法解析的服务端 JSON 或未完成的服务响应，完整重跑该块一次。重跑沿用原顺序和 seed，从三个空历史开始。全部尝试留档，主分析按 D2 规则使用重跑尝试，仍有失败的槽照常记账。首轮只有一次基础设施失败时原块直接入分析。模型文本为空、不可提取、越界、观测不一致或重复时均消耗预算。分别报告计划槽位、实际请求、HTTP 成功、完整模型响应、重跑块与重跑请求。 [D2 故障与记账协议](d2_prompt_report.md#a-请求数量与基础设施)

## 4. Ground Truth 隔离与原始数据

**在线采集。** 样本数据只来自去标签的 `online_manifest.json`，限定为 Group ID、公开观测、Prompt 模板及预注册的运行参数、请求顺序与 seed。历史按条件和尝试在进程内独立维护，由官方文本 Parser 提取。Guard 只记诊断。入口验证 `freeze.json` 和 `preflight.json` 的完整 Schema、文件哈希、预注册环境和逐项通过状态，随后启用文件读取限制。运行计划固定，无在线 Controller 或 Reward。

启动前对实际交付给采集入口的 manifest 实施字段白名单。根对象只允许模型标识、digest、options、templates、blocks 和重跑阈值。块对象只允许块 ID、Group ID、公开观测、rollout seed、槽 seed 和 Prompt 顺序，公开观测的渲染文本与选定组逐条对照。检查 manifest 对象和冻结收据没有 `ground_truth_expressions`、答案数量及结构、兼容表达式列表或离线评分结果。冻结收据只提供核验和运行元数据。原答案文件与离线评分保留在独立离线进程一侧。

P3 采集入口为 `scripts.run_d2_prompt --p3 <run_dir>`。生产入口在打开请求日志前校验字段白名单、公开观测、H1–H5 与 Prompt 哈希、每块的 Seed 和 Prompt 顺序，以及 180 个计划槽位。主进程读取在线清单、两份收据及用于哈希核验的脚本。独立的本地哈希进程校验答案集和选择清单的原始字节，只向采集主进程返回两个 SHA-256。测试追踪主进程的文件访问，确认它未直接打开这两个文件，并在进入采集阶段后拒绝读取答案、选择材料和离线评分文件。子进程 Mock 通过这一真实入口执行，审计钩子禁止网络。 [生产校验](../scripts/run_d2_prompt.py) · [收据校验](../scripts/p3_preflight.py) · [离线预检测试](../tests/test_p3_validation_preflight.py)

**独立评分。** 生成结束并封存日志后，在独立进程加载同一版本答案集。固定上游 commit 为 `c69e9318577b34b5b896996571aefd4ba6053f58`。核对原始 HTTP 正文字节与其中的模型字符串，先按 §3 为整个块选择分析尝试，再将该尝试的每个槽送入 `evaluate_single_observation_set(..., max_retries=1)`。成功完成的模型响应按封存原文回放。选定尝试中的基础设施失败使用官方 `Error querying` 标志进入无效槽，即使未完成的正文中含部分 `response` 字符串，也完整留档。Guard 诊断独立记录。需要安全复核的原文沿用 D2 的审阅流程，完成回放后才出分。 [官方回放口径](algorithm_design_v2.md#官方回放与-guard-隔离)

**P3 离线评分入口。** 运行日志封存后，从仓库根目录调用 `.\.venv\Scripts\python.exe -B -m scripts.score_p3_prompt <run_dir>`。入口核对 Freeze 中的评分入口、本地依赖和固定且干净的上游，并验证 `collection_seal.json` 对整个请求日志、Freeze、Preflight 和在线清单的绑定。评分直接使用已核验的日志字节。随后逐槽依据原始 HTTP 状态、传输错误及 JSON 复核归档文本和失败标志。从官方 Parser 的重新提取结果计算 Guard Pass，逐条比对包括被整块重跑替代的尝试。任何不一致均拒绝评分。已完成的空模型文本原样交给官方 Parser。基础设施失败的部分文本及原始正文完整留档，评分入口传入官方错误标志。复评分时复制封存输入到新的目录，评分器拒绝覆盖已有评分文件。 [P3 评分入口](../scripts/score_p3_prompt.py)

**一槽一次的离线证据。** 混合成功、不可提取与基础设施错误的四槽 Mock Replay 在 `max_retries=1` 下严格消费四条记录。`max_retries=2` 的对照中，两槽的首槽失败会多消费一条。完整矩阵的 Mock 共归档 192 条记录，评分只消费预注册选择的 180 条，覆盖 45 条官方评分轨迹，每个条件 60 槽。两次块尝试均完整保存。离线评分前逐槽使用官方 Parser 从已完成的封存原文重新提取候选。与归档的 `parsed_expression` 不一致时拒绝评分，并报告块、尝试、槽位及条件。基础设施失败不进入任何候选历史。 [离线预检测试](../tests/test_p3_validation_preflight.py)

**计划保存位置**为 `results/p3/controlled-validation-<run_id>/`，本轮不创建运行目录。批准后每次使用独立目录。

## 5. 评分指标与放行标准

所有槽率分母为该统计窗口的计划槽位，缺失的基础设施槽照上述协议记账。官方指标使用官方返回值。逐槽诊断单列，不改变官方定义。

| 指标 | 定义 |
| --- | --- |
| **Official RR（主指标）** | 官方 `recovery_rate`。每条轨迹用有效去重候选的机械键匹配官方答案键，再以该组官方答案键计数为分母。先算每条轨迹，再对 15 条等权平均。 |
| Parse Success | 官方 `parse_success_rate`，从响应成功提取候选的槽位比例。 |
| Guard Pass | D2 语法 Guard 诊断通过的槽位比例。 |
| In-space Rate | 官方 `in_space_rate`，满足官方空间约束的槽位比例。 |
| Official VR | 对每个 Prompt，**官方有效输出槽数 ÷ 60 个计划槽位**。因为每条轨迹固定四槽，这等价于 **15 条官方 `valid_rate` 的等权平均**。包含重复有效表达式。分析所选的尝试中，未被整块重跑替代的基础设施失败槽计为无效，仍占分母。 |
| Official NR | 官方 `novelty_rate`，轨迹内空间合法且不同的机械键数除以槽位数，含观测不一致的空间内键。 |
| First Valid Novel Discovery Rate | 空间内、通过官方观测验证且本轨迹首次出现的有效机械键数除以槽位数。 |
| NOT/NOR Rate | 原始文本含独立 `NOT` 或 `NOR` 词项的槽位比例，忽略大小写，另列各词计数。与 AST 空间判定分开。 |
| AST Depth Violation Rate | 官方 AST 可构造且真实深度大于 2 的槽位比例。允许与禁用算符重叠，另报 AST 无法构造的槽数。 |
| Example Mechanistic Key Rate | 通过空间检查且官方键匹配 `x AND y` 或 `x OR y` 的槽位比例。两键分开列计数，并报告其中观测验证有效的次数。 |
| Duplicate Rate | 当前轨迹内重复出现的空间内机械键槽数除以槽位数。另报原始文本完全重复和有效机械键重复，避免把三种重复混为一谈。 |
| Prompt Token 成本与耗时 | 对 P1、P2、P3 分别汇总 `prompt_eval_count` 和 `eval_count`，报告输入与输出 Token 合计、记录可用数和平均请求耗时。主表使用分析所选尝试，另给所有实际请求的成本以计入重跑。Token 缺失时记为 `null` 并报告缺失数，耗时平均包含对应表内已计时的失败请求。 |

在 `official-results.json` 中，深度和重复率分别记录在每个条件和每条轨迹的 `diagnostics`，原始深度及重复标志在 `by_slot`。每个条件的 `request_cost` 分别给出 `selected_attempts` 和 `all_attempts`。Token 有效记录要求输入和输出计数均存在，两个方向也各自报告可用记录数及合计。某个方向完全缺失时其合计为 `null`。有计时的失败请求纳入算术平均，并报告有效耗时记录数。

每个 Prompt 分别核对两项原定放行条件。**汇总 Official VR ≥ 25%**，且**至少两个 rollout seed 各有至少 4/5 个 Group，每个有效组至少产生一个官方有效候选**。两项都通过才具备提请审查 Pilot 的资格。RR 用于研究比较，Pilot 仍需单独批准。P3 的结果不触发改动门槛。 [原放行规则](algorithm_design_v2.md#2-d2-prompt-对照协议)

## 6. 配对与统计协议

分析单位是 **15 个 Group–Seed 配对单元**。预先固定比较方向 `P2−P1`、`P3−P1`、`P3−P2`。报告每个组–种子的官方 RR、VR 和是否至少一次有效，各 Prompt 总体等权宏均值、逐组跨种子均值、逐种子跨组均值，以及各配对差的均值、样本标准差、中位数和正向／持平／负向单元数。有效组数按种子列出 `n/5`，另汇总 15 个单元中有效组出现的次数。配对中单元的推进条件统一，以免比较时对某个版本筛掉失败轨迹。

- **Q1。** 首槽历史为空。对同一配对单元的首槽用官方 Evaluator 按一槽回放，仍使用完整组答案分母，比较直接 Prompt 表现，并给出解析、空间、有效、示例键与首次发现的计数。
- **Q2–4。** 候选来自各自的历史，按全轨迹前缀去重。报告三槽的 VR、有效新键率和官方 RR 的后段增量 `RR(Q1–Q4) − RR(Q1)`。另报只在后段才第一次出现有效候选的组数。前后段差异按轨迹现象解释。
- **证据范围。** RR 为主指标，其他指标用于定位变化。三种 Prompt 的 180 个槽不作为 180 个独立样本。同一观测组跨种子复用，因此以描述性配对分析为主，不预注册基于槽独立的显著性检验。分别报告 P1–P3 和 P2–P3 的解释，保留已声明的少量组与缺少四观测留出层的限制。

## 7. 资源与风险估算

估算基于 D2 同模型、同请求预算和参数。D2 实测 180 次成功请求从首请求开始到末请求完成为 **63.42 秒**，每条件的 HTTP 中位约 0.26–0.28 秒，P95 约 0.36–0.44 秒。RTX 4060 Laptop GPU 总显存 **8,188 MiB**，54 个完整样本的整卡显存峰值为 **4,861 MiB**。采集结束时模型显示 **100% GPU、上下文 4096**。这些数值用于估算，不代表当前机器的已检状态。 [D2 耗时与显存](d2_prompt_report.md#k-模型耗时显存与失败案例) · [GPU 原始采样](../results/d2/prompt-20261126/gpu-samples.csv) · [Ollama 运行记录](../results/d2/prompt-20261126/ollama-after.txt)

| 项目 | 预估与依据 |
| --- | --- |
| 180 次正常采集 | **约 1–2 分钟**。以 D2 的 63.42 秒为基准，为冷启动、提示长度和后台负载留出余量。另预留离线校验及文件检查时间。 |
| 原始日志 | D2 的 180 条 `requests.jsonl` 为 **1,292,134 B（约 1.23 MiB）**。本次原始日志预计 **1.2–1.6 MiB**。全套运行文件先预留 3 MiB，如需保留大批重跑则预留 6 MiB。 |
| 单次整块重跑 | 额外 **12 个请求**，服务恢复正常后约 **4–6 秒**，估计原始日志增加约 **84 KiB**。 |
| 重跑总上限 | 15 个块各最多重跑一次，最多额外 **180 请求**，全部日志留存。若额外请求速度接近 D2，采集额外约 1–2 分钟。连接或响应超时沿用 D2 的 120 秒客户端超时设置，连续故障会显著放大耗时。 |
| 失败风险 | 服务不可用、模型标签或模板发生变化、可用显存不足、GPU 回退及日志写入失败会影响采集。启动前先核验固定版本和显存，按块记账与保留失败日志。格式不合规和观测不一致是研究结果，进入预注册评分。 |
